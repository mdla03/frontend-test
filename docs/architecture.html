Spaces · Architecture

How a request travels from the browser to the database

Spaces is the internal community-events platform for Manulife Philippines — employees discover and join events, organizers run them, admins approve both. Three tiers, one enforcement point, four tables.

Why the API tier exists. Supabase can be called straight from the browser. It deliberately isn't: that would push every rule into Row Level Security policies and put a database credential in the client. One enforcement point in Express keeps the rules in one place — and keeps the frontend portable to any Postgres later.

Figure 2Request lifecycle

Every protected call takes the same four steps. The order matters: authentication before role, role before ownership.

Three depths, not one. Role alone would let any organizer edit any other organizer's event. The ownership comparison lives in the controller, where the row is already loaded — and it still lets an admin through.

Figure 3Event lifecycle

The product's central rule: an event is invisible and unjoinable until an admin approves it. Registration re-checks approval at join time, so an event rejected between page load and click cannot be joined.

Cancelling is a state change, not a delete. The row survives so history does. Combined with the unique (event_id, user_id) constraint, re-joining has to be an upsert on that pair — a plain insert would violate the constraint.

Promotion closes its own loop. An employee applies, an admin grants the role, and the next protected route entry re-syncs the cached user from /me — the organizer portal appears without logging out and back in.

Figure 5Data model

Four tables. Every status column is a check constraint rather than a Postgres enum, so a migration can widen the allowed values without an ALTER TYPE.

  users {
    uuid id PK
    text email UK
    text password "bcrypt, cost 10"
    text role "user|organizer|admin"
    text organizer_status "none|pending|approved|rejected"
  }
  events {
    uuid id PK
    text approval_status "pending|approved|rejected|changes_requested"
    text status "submitted|cancelled|completed"
    geography location "point 4326"
    double latitude
    double longitude
    uuid organizer_id FK
    uuid approved_by FK
  }
  event_registrations {
    uuid event_id FK "cascade on delete"
    uuid user_id FK "cascade on delete"
    text status "registered|waitlisted|cancelled"
    constraint unique_pair "unique (event_id, user_id)"
  }
  rewards {
    uuid user_id FK "cascade on delete"
    uuid event_id FK "set null on delete"
    numeric amount
    text status "pending|granted"
  }

Referential policy is decided per relation, not globally. Deleting an event cascades its registrations — a registration means nothing without its event. The same delete only nulls the link on a reward, because a granted reward records something an employee actually did and has to survive the event being removed.

Where each concern lives

Authentication
authMiddleware, mounted with router.use() at the top of every protected router — a route added later is guarded by default.
Role
requireRole('organizer') — a small factory returning middleware.
Ownership
Inside the controller, where the row is already loaded.
Visibility
In the query itself. A user gets approval_status = 'approved' appended — unapproved events never leave the database.
Capacity
Counted by Postgres. Event queries embed event_registrations(count), so remaining slots arrive with the event in one round trip — no N+1, no counter that can drift.
Geo search
ST_DWithin in the nearby_events function, ordered by distance. Coordinates are stored twice on purpose: plain doubles for the client, a geography column for the query.
Client state
useAuth over localStorage. No Redux, no Context provider — there is exactly one piece of global state, and it is the signed-in user.

Read alongside the diagrams

  • The token carries sub and role, but role is re-read from the database every request. Costs one query; buys instant effect when an admin demotes someone, instead of waiting out a token expiry.
  • Env vars fail fast. required() throws at import time, so a missing key stops the process at boot with a named error rather than surfacing as confusing 500s later.
  • Cover images are size-capped. Covers arrive as base64 data URLs, so the JSON body limit is 4 MB and an img_url over 2 MB is rejected with a 413.
  • The API uses the Supabase service_role key, which bypasses Row Level Security entirely. Workable while Express is the only client. Before any direct browser-to-Supabase access, RLS policies become mandatory — and a key copied between machines should be rotated.
  • Capacity is displayed but not enforced server-side, and the waitlisted status is unused. Enforcing it needs a transaction or a trigger; a check in JavaScript races under concurrent joins.
